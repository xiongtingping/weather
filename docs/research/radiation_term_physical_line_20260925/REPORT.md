# 物理线 vs 温度线：P0 辐射降温项由 TAF / METAR 继承修正——没有可服务的信息增益（2026-09-25）

## 结论

**没有可服务的信息增益，不改服务。** 物理线（TAF / METAR 的云、雨、风去继承并修正 P0 的辐射降温项、再平移分布）与温度线确实是两条线，但物理线里有信息的部分已经被用掉了：

1. **P0-M（TAF 的物理证据）：零增益。** 早间 TAF 的云/雨/风在「温度线＋模式自身物理」之上 **−0.0014 nat [−0.0040, +0.0012]**，前一晚 −0.0016；「修正」形式（TAF 减模式、再按站扣掉量纲偏差）−0.0005；只用 AWC 近 29 天 45 站、只用带 TX 的 TAF 都是负的。按生产 0.07 系数不拟合地「字面继承」（TAF 云经 Kasten–Czeplak 改 Kt）**−0.018 [−0.024, −0.012]**，明确变差。连「完美 TAF」——事后用 METAR 实测的当天升温窗云/雨——也只值 **+0.0088**，TAF 一点都没拿到：模式自己的辐射/云预报已经说了 TAF 说的云（与 209 条（二）同一结论，换接法、换数据、换 16 个月仍成立）。
2. **P1（METAR 的物理证据）：有信息，但就是「此刻」那一份，生产已在用。** 相对纯温度线，METAR 此刻的云/降水/风/露点差 **+0.0024～+0.0075 nat**（08–16 时全部区间 >0）——这正是宪章 150/161 直接更新已服务的特征。在它之上，整条物理线（已过时段实况−预报、继承的 TAF 余下时段修正、P0 辐射项重加权）只剩 **+0.0003～+0.0013**：按协议判据，只有 14 时（+0.0009 [+0.0003, +0.0016]）与 16 时（+0.0013 [+0.0006, +0.0020]）算「有信息增益」（Brier 同为正、前后两半同号），但都不到服务门槛（0.01 nat）的七分之一；而且拟合出的 TAF 云/雨系数符号反物理（TAF 报更多云雨→更暖），是天气型的标签而不是辐射修正，另一半来自把 P0 辐射项削弱（系数为负），属 P0 系数问题。「已过时段实况−预报」单独有一点信息（+0.0006～+0.0026），但在此刻状态之上为零：**已经发生的云，已经写进了温度曲线**。
3. **继承本来就在。** P0-M＝P0×L_TAF、P1＝根×掩码×exp f，P0 的辐射平移随根进入两阶段；本研究测的是「修正」，修正不付账。
4. **复刻可信度**：四家全球模式代理上，生产的 0.07 辐射项本身 **+0.0026 [+0.0013, +0.0039]**，与宪章 210 在生产数据上的方向一致；best_match 代理上该项为负（区域高分辨率模式已吸收辐射耦合），故以全球代理为主、best_match 仅作敏感性——两者对物理线的结论相同。

## 怎么读

- **为什么 P0-M 没有**：TAF 的云/雨是预报员对同一批模式云场的判读。复刻的 5,485 个早间 TAF 站日上，TAF 升温窗云与模式升温窗云相关 +0.644、与 P0 的 Kt z 相关 −0.574，TAF 降水概率与模式湿时段相关 +0.558（209 条在生产上测到 TAF 云与 P0 辐射读数相关 −0.358，同向）；把模式物理放进基线后 TAF 的增量归零。上限臂说明「当天云雨到底怎样」在 P0-M 时刻值 +0.009 nat，但这份信息 TAF 事前并不比模式多知道。
- **为什么字面继承变差**：TAF 云是「最厚一层的成数」（FEW/SCT/BKN/OVC＝0.125/0.375/0.75/1），模式云是总云量百分比，两者直接代入辐射式后平均 |Δz|＝1.38，相当于每天给 P0 加一个与真值无关的噪声平移。
- **为什么 P1 此刻状态有而其余没有**：余下几小时能升多少，取决于**现在**的云和雨会不会持续（持续性）；已经过去的云的影响已写进实测温度与「近 3 小时对曲线的偏差」，再加一遍是重复计数。
- **小而显著的 P1 晚间读数**：14、16 时约 +0.001 nat，拆开看来自「继承的 TAF 余下时段」与「P0 辐射项重加权」两项，前者符号反物理，后者方向是削弱 P0 辐射项——都不是「物理线修正辐射项」的形状，也都远低于服务闸。
- **不改的**：服务算术、版本、账本指纹、宪章条款均未改动；本研究不据复刻数据提议改 P0 辐射系数（复刻的 P0 是代理）。〔后续：熊先生裁决把系数拆成两侧，见「裁决」一节与宪章 222。〕

## 追问：为什么只有降温，没有升温（2026-09-25）

熊先生：「为什么只有降温，没有升温」。`asymmetry.py` → `results_asymmetry.json`，同一批复刻数据。

**名字叫「降温项」，算术是双向的**：0.07·Kt z·σ，预报比本站近 180 天晴（z>0）就往暖推，阴就往冷推；复刻 20,035 个站日里 **58.7% 往暖推**。看上去「只有降温」，是因为晴有上限、阴没有下限：晴朗度 Kt 顶多到晴空透过率，晴天全挤在上沿（z 中位 +0.26，正侧均值 +0.72、最大 +2.62），阴天拖一条长尾（负侧均值 −1.04、最小 −9.01，偏度 −1.05）。于是往暖的平移都很小（均值 +0.06°C、最大 +0.27°C），往冷的平移又大又显眼（均值 −0.09°C、最低 −0.73°C）。

**数据说的恰好相反——信息在升温侧**。把辐射平移前的残差（σ 为单位）分别对 z 的正、负两段回归（事件日自助 95%）：

| P0 代理 | 升温侧（z>0）每单位 z | 降温侧（z<0）每单位 z |
|---|---|---|
| 四家全球模式（主） | **+0.158 [+0.121, +0.197]**（在役 0.07 的 2.3 倍） | +0.020 [−0.006, +0.044]（≈0） |
| 　前半期 / 后半期 | +0.135 / +0.179 | +0.048 / −0.009 |
| 　北半球温带 / 热带与南半球 | +0.178 / +0.105 | +0.022 / +0.016 |
| best_match（敏感性） | +0.067 [+0.032, +0.101] | −0.071 [−0.098, −0.048]（方向反了） |

即：比平常晴的日子，实况比模式更暖，而且暖得比在役系数给的多；比平常阴的日子，模式自己已经降够了温，再往冷推没有依据（best_match 上甚至推错方向）。这与 209 条（四）在生产上测到的「阴雨预报对应的降温在 P0 被用了约两倍」同向。

**换成服务读数，差距很小**：逐日前推打分，只留升温侧对在役对称 0.07：全球代理 +0.0005 [−0.0006, +0.0016]（不显著），best_match 代理 +0.0041 [+0.0026, +0.0055]；分两段各拟合（不对称）对在役：+0.0004 [−0.0006, +0.0014] / +0.0049 [+0.0029, +0.0069]。生产窗口（08-16..09-24，40 天）在复刻上太短，两侧区间都跨零。

**P1 也是双向的**：前文例表只列了「晴→阴」方向；反过来「阴→晴」各档乘数是倒数（14 时前：1 / 1.10 / 1.40 / 1.78 / 2.26，「阴且下雨→晴干」1 / 1.59 / 2.36 / 3.51 / 5.22），露点差大（空气干）也抬高再升概率（+5°C → 14 时前再升几率 ×1.28）。P1 唯一真正单向的是硬下界：已报最高以下的档永远是 0，所以 P1 的「降温」只能是「少升一点」，不会低于已观测。

**建议**：升温侧/降温侧拆开是 P0 辐射系数（第 160/173/210 条）的问题，不是继承修正结构；复刻证据只到「方向一致、全球代理上服务增益不显著」，改系数须先在生产服务向量上复测（P0 回执 `synoptic_cooling_json.standardised` 与服务向量都在，`asymmetry.py` 的拟合换成生产根即可），再交裁决。
